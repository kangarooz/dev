---
description: Interactive onboarding - ask for the feature, URL, display, login and steps, scaffold scenarios/<slug>.json, inspect the app, fill selectors, validate, dry-run (TUI only)
agent: demo-smoke
---
Onboard one new demo scenario by asking the user questions, then scaffold, inspect, fill in, validate and dry-run it. Optional starting hint from the user (a feature name, or empty): $ARGUMENTS

This command needs the `question` tool and only works in the interactive TUI (`opencode`, then `/onboard`). If the question tool is not in your tool list (that is what `opencode run` does), reply exactly: `onboard needs the TUI: run "opencode" in the kit directory, then type /onboard` and stop.

Rules for this command: one tool call per step. Ask with the question tool only, `custom` left on so the user can type. Every option is an object `{"label": "...", "description": "..."}`: the options below are written `label | description`, and when there is no ` | ` repeat the label as the description. The recommended option says `Recommended:` at the start of its description, never in the label. The answer is the chosen label (or the typed text) exactly as written; a description is never part of an answer. Never ask for a password or any secret value, only for the NAMES of environment variables. Never run `creds set` yourself (it is denied; it needs the user's terminal). Use `python`, or the venv interpreter from your instructions, in every command. `<slug>` is the feature name in lowercase with dashes (`Chat with Manuals` -> `chat-with-manuals`). `<headless>` is `--headless` when the Display answer was `No display`, otherwise nothing.

1. Question, header `Feature`, question `What is the feature called? (used as the scenario name and slug)`, options: `<hint> | Recommended: the name you gave` where `<hint>` is the hint above without its surrounding quotes, or `Chat with Manuals | the example feature` when the hint is empty. Remember the answer as `<name>`.
2. Question, header `App URL`, question `Where is the app running? (the scenario opens this URL first)`, options: `http://localhost:3000 | Recommended: the usual dev server`, `http://localhost:8080 | another common dev port`, `http://127.0.0.1:8765 | the kit's mock app (tests/fixtures/app)`. Remember the answer as `<url>`.
3. Question, header `Display`, question `Can Chrome open a window on this machine?`, options: `Yes, it has a screen | Recommended: you will see the browser while it runs`, `No display | a server or CI box: every browser command gets --headless`. Remember `<headless>`.
4. Question, header `Login`, question `How does the app log in?`, options: `none | Recommended: no login page`, `form | a username/password page`, `basic | HTTP basic auth (browser popup)`. Remember `<login>` = `none`, `form` or `basic`.
5. Only when `<login>` is `form` or `basic`: question, header `Credential names`, question `Which environment variable NAMES hold the username and the password? (names only, never the values)`, options: `DEMO_USER and DEMO_PASS | Recommended: the kit's default names`. The first name is `<user_env>`, the second `<pass_env>`. When `<login>` is `none`, skip to step 7.
6. Only when `<login>` is `form`: question, header `Login page`, question `Which path shows the login form?`, options: `/login | Recommended: the usual path`. Remember `<login_path>`. Then run `python -m demo_smoke inspect <url><login_path> --out demo-output/<slug> <headless>` and, from its table (see step 11 for the columns), remember the `selector` of the username input as `<user_sel>`, of the password input (kind `input:password`) as `<pass_sel>` and of the sign-in button as `<submit_sel>`. Exit 3 (`error:` line): report it and stop.
7. Question, header `Step 1`, question `Describe step 1 of the happy path as "Title :: what the user does and what should be visible after it"`, options: `Open the app :: open the home page and see the main screen | Recommended: nearly every demo starts here`. Remember the answer as one `--step` value.
8. Repeat with header `Step 2`, `Step 3`, ... and the question `Describe the next step as "Title :: what happens and what should be visible", or pick Done`, options: `Upload a file :: choose a file and see it listed | a file input`, `Ask a question :: type a question and see an answer | a text box and a button`, `Open a detail :: click a result and see its details | a link or a list entry`, and from step 4 on also `Done | no more steps` as the first option (the user needs 3 to 6 steps). Stop asking after `Done` or after step 6.
9. Run `python -m demo_smoke init-scenario --name "<name>" --url <url> --out scenarios/<slug>.json --login <login> --step "<step 1>" --step "<step 2>" ...` - add `--username-env <user_env> --password-env <pass_env>` when `<login>` is not `none`, and `--login-url <login_path> --username-selector "<user_sel>" --password-selector "<pass_sel>" --submit-selector "<submit_sel>"` when it is `form`. It writes no log file; its result is the `init-scenario: ok` line. Exit 4 (`error:` line): fix exactly the reported argument once and rerun; if the line says `scenarios/<slug>.json exists`, ask the question, header `Overwrite`, `Overwrite scenarios/<slug>.json?` with options `Yes, overwrite | replace the existing file`, `No, stop | keep it and stop`, and rerun with `--force` only on yes.
10. Only when `<login>` is not `none`: print these two lines for the user to run in their own terminal, exactly:
   `python -m demo_smoke creds set <user_env>`
   `python -m demo_smoke creds set <pass_env>`
   Then ask the question, header `Credentials`, `Did you run both creds set commands in your own terminal? (the values go to the kit's .env, which I never read)`, options: `Yes, both are set | check them now`, `Skip for now | login will fail until they are set`. On yes run `python -m demo_smoke creds check <user_env> <pass_env>` (its result is on stdout, there is no log file); on exit 4 (`MISSING`) ask that question once more, then continue and note in the report that login will fail until they are set.
11. Run `python -m demo_smoke inspect <url> --out demo-output/<slug> <headless>` - add `--login-from scenarios/<slug>.json` when `<login>` is `form` or `basic` and the credentials are set. It prints a table with the columns `#`, `kind`, `selector`, `text / placeholder`, one row per input, button, link and file input: use the `selector` column (the first column is only the row number). A selector followed by `(xN)` matches N elements: prefer another row, or append ` >> nth=0` to it. Then read `demo-output/<slug>/logs/inspect.json`. Exit 3 (`error:` line, Chrome or URL problem): report it and stop. Exit 2 (`inspect: FAIL`, login failed): tell the user the login selectors or credentials are wrong and continue without login.
12. Read `scenarios/<slug>.json` with the read tool. For every step, replace `"actions": []` and `"expect": []` using selectors from the inspect table and delete the step's `todo` key. Actions, in order, one object each: `{"goto": "/path"}`, `{"click": "<selector>"}`, `{"fill": {"selector": "<selector>", "text": "..."}}`, `{"upload": {"selector": "input[type=file]", "files": ["fixtures/osha-1910.pdf"]}}` (the kit's only fixture; if the user named another file in the step description, use its path relative to `scenarios/`), `{"press": "Enter"}`, `{"wait_for": {"selector": "<selector>", "timeout_s": 10}}`. Expectations, at least one per step: `{"text": "words visible on screen"}`, `{"selector": "<selector>", "contains": "words"}`, `{"selector": "<selector>", "count_min": 1}`, `{"url_contains": "/path"}`. Then write the whole file once with the write tool (valid JSON, no `todo` keys, no other keys added; the `login` block stays as init-scenario wrote it). If a step needs a page you have not inspected, run `python -m demo_smoke inspect <url>/<path> --out demo-output/<slug> <headless>` once for it first.
13. Run `python -m demo_smoke validate scenarios/<slug>.json --out demo-output/<slug>` and read `demo-output/<slug>/logs/validate.json`. Exit 4 (`validate: INVALID`, one `error:` line per problem): fix exactly those problems once with the write tool and validate again; still invalid: stop and report them. `warning:` lines: one ending in `then remove this key`, `no actions` or `no expectations (nothing is checked)` means step 12 is incomplete for that step id: finish it, then validate again (once); one starting with `login.` means the credentials are still missing (report it, do not edit the scenario); `upload file not found` means fix the `files` path.
14. Run `python -m demo_smoke dryrun scenarios/<slug>.json --out demo-output/<slug> <headless>` and read `demo-output/<slug>/logs/dryrun.json`. Exit 2: read `demo-output/<slug>/logs/smoke-results.md`; if a selector was not found, run inspect once on that page, fix the scenario once with the write tool, and run dryrun once more. Exit 3: report the `error:` line and stop.
15. Reply with: the scenario path, one line per step with its dryrun status, the credential names still missing (if any), and the exact next commands:
    `/smoke scenarios/<slug>.json demo-output/<slug>` (append the reference clip, e.g. `voices/mine.wav`, when `/clone-voice` produced one; append `headless` when `<headless>` is set)
    `opencode run --agent demo-smoke --auto --command smoke "scenarios/<slug>.json demo-output/<slug>"` for the unattended version.
